# Direct 与 DeepEval 生成对照设计

用户已授权分别实施并对比，沿用当前会话顺序实施、不反复确认、不提交推送的约定。

目的：在当前 query_user v3 的42槽位上，比较直接调用模型和DeepEval生成工作流的实际价值。两轮顺序Direct→DeepEval、DeepEval→Direct，共168个最终场景输入目标；每臂25个可生成Oracle槽位、17个已知契约缺口仅生成输入。

相同条件：同一个 .env 指定的DeepSeek模型、同一IR/来源清单/覆盖计划/候选Schema、同一槽位描述、temperature=0.4、thinking disabled、max_tokens=4096、每槽位最多3次完整尝试、无隐藏网络重试、同一确定性验收和归一化去重。保留全部请求正文（不含认证头）、响应正文、usage、耗时、attempt、原始Golden及失败原因。两个生成器不读取种子、不共享候选或反馈。

采用一个共用的显式参数Provider包装器，供直接生成和DeepEval native模型适配使用，解决原SDK无Schema调用遗漏temperature的问题。SDK的多阶段提示词和评分流程保留，直接路径每次尝试只请求一次JSON。源事实/槽位任务一致，阶段提示词和模型调用数量是被比较的差异，不声称完整Prompt相同或等token预算。

方案比较：历史scripted对比不能衡量真实生成；一次A/B容易受先后顺序影响；采用两轮交换顺序，仍属小样本工程实验，不作统计显著性或跨任务泛化结论。只新增独立实验入口和可复用Direct槽位生成器，不替换生产CLI默认后端。

验收：报告每臂42槽位首试通过率，另列25个Oracle槽位与17个input-only槽位；最终完成率、拒绝原因、重试数、语法/契约/场景错误、精确/归一化重复、表达集中度、API调用、input/output/cache tokens、耗时。已知契约阻塞不是生成错误，不计为通过可执行用例。最终25候选进行同样的子集质量/泄漏/去重检查。

人工修改量尚无真实人工数据，以隐藏臂标签、随机顺序的AI初审记录待修改/待确认项作代理，明确不等于人工批准或审核工时。原始产物不改写，不自动冻结。

试验前记录所有既有suites/workspaces文件哈希。实验失败也保存审计并继续其他槽位，禁止只选最好的一轮；两轮均纳入报告。比较过程中不根据某一臂结果改约束或Prompt。计费缓存无法主动清空，分别报告实际cache使用和不含缓存折扣的归一化用量。
